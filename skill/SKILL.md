# 软通案件批次制作

用于这台 Windows 主机上的案件流水线。项目根目录是 本技能安装时绑定的项目根目录，配置为 `config.json`，执行器为 `scripts/caseflow.py`。先确认这些文件存在，再使用实际脚本帮助。不要把通用文档编辑或化工材料附图任务误送入本流程。

用户已确定：仅在明确要求执行时启动，每批给一个目录，清单确认后整批执行；工作区在 项目根目录下的 `cases`，成品在原料目录同级的“原目录名1”；保留原件。GPT-6.1 Sol high（高）负责建设与自检，GPT-6.1 Sol ultra负责返修，普通案件由GPT-6.1 Sol ultra独立判断最终图表、界面、Word和视频；用户明确加急时由GPT-6 Astra low在独立加急槽验收。不要询问这些已决定的偏好。没有明确启动要求时，不扫描目录、不制作、不学习其他任务，也不安排定时唤醒。

日常入口对话建议选 GPT-6.1 Sol / 高；本技能不改变入口对话的模型，脚本为案件执行阶段单独固定模型。用法与消耗控制见 [开始使用](../开始使用.md)。

工作区固定为 `cases/YYYY-MM/案件名`（相对于项目根目录），按首次登记月份归档；同月重名加“（2）”等序号，不用哈希作新案件目录名。批次管理文件在cases/.batches，内部身份编码仍用于校验与恢复。默认8案并行建设，普通独立验收3共享槽、录制默认2槽（内存准入保护；受控证据1槽）；每案有独立资源配置，不手动启动多个同批执行器。已有批次锁定时禁止重复运行，运行中的旧目录不移动；旧进程不会热加载新调度代码。用户明确要求更替当前旧执行时，先保存状态/成果哈希、核实归属后停止旧执行器/worker/本案服务，再用 `.\scripts\caseflow.ps1 migrate "<目录或批次ID>"` 迁移，完成后run恢复；已授权的切换不重复询问。迁移复用已有代码/Word/图表、保留原件/历史调用和计数；先Sol修复路径与文案，再重录重验。迁移未完成时run拒绝启动，重试同一migrate恢复，不能另开同批。普通run仍兼容未迁移旧案。

## 固定成品交付结构（所有后续案件）

用户2026-09-30确定的长期交付规则：以后本项目所有案件与批次的成品交付均采用“每案根目录放修订Word、每案自己的模拟系统子目录放视频”。普通交付、加急交付、经用户授权的提前导出和返修后另存成品均遵循此结构，不限于0928批次。除非用户之后明确更改，不得将Word与MP4平铺，也不得把多案视频混放到批次共用目录。发布前核对最终相对路径与文件哈希并同步清单/收据；仅调整目录不触发重录、重验或内容返修，历史成品不因此自动重打包。

```text
批次成品目录/
└─ 案件名称/
   ├─ 修订文档.docx
   └─ 模拟系统/
      └─ 演示视频.mp4
```

“只交付一个Word和一个视频”指成品内容范围，视频仍必须保留上述子目录；具体文件名沿用本案命名。建设目录、源码、数据、图表与过程证据继续保留在案件工作区。

## 执行

1. 读取 [质量规则](../rules/requirements.md) 和 [成果合同](../docs/artifact-contract.md)。仅当需要架构或故障背景时读 [设计方案](../docs/architecture.md)。
2. 同时读取[用户实际改图标准](../rules/chart-acceptance.md)。收到材料目录后，使用 `.\scripts\caseflow.ps1 plan "<目录>"`，工作目录设为项目根；它读取配置中的bundled Python和工具路径。plan不调用模型、不修改原件。向用户给出案件清单、数量、异常、工作区和成品路径。示例/对比目录不能直接run；同一批清单已被明确确认就继续，不再重复要求确认。
3. 确认后执行同批 `run "<目录或批次ID>"`；`--dry-run`仅用于检查路由方案，不能当真正完成。脚本负责明确模型选择、阶段顺序和状态，不需手动新建侧栏任务、选工作区、复制命令词；不要擅自另建定时任务。
4. 运行期间读取状态和日志并报告有意义的进度；支持长期shell会话，但不要留下无主进程。用 `status "<目录或批次ID>"` 查看。失败案件留待处理，其他独立案件继续。恢复前确认输入未改变、进程没有重复运行和旧质量审核仍对应当前证据。遇工具/权限/模型不可用如实说明，禁止通过改sandbox、禁用策略或换低配模型来绕过。
5. 完成时按实际状态汇报已通过/待处理/失败、成品位置、剩余条件。查看最终文件清单与哈希；未经全部关卡不得称已完成。源文件、历史成品和其他项目进程不能修改。

用户要求学习其他改图任务时，只读那些任务的用户反馈、公开最终回复和相关图像，保存带哈希快照与版本，更新本项目规则。区分明确用户认可、独立验收者验收、助手自称完成和仍在修改；“插入Word/打开web/停止项目”只能作为流程推进信号。不要把这一要求变成未经请求的定时监控，也不要向其他任务发送修改指令。

## 质量约束

后续新批次重点执行[图例与数据系列对应](../rules/chart-legend.md)：图例名称与实际数据/工况一一对应，线型、标记、灰阶、柱形填充和纹理与图中一致；PNG、网页及Word最终显示均逐图核对，防止错位、遗漏和样式不符。按[本次生效范围](../rules/chart-legend-scope.json)执行，其中已登记批次及未完成案不因此返修、重录、重验或重启。纳入现有Sol自检与Ultra验收，不额外增加固定审查轮次。

用户2026-09-28的新偏好只用于后续新批次，详见[专业图表与公式符号](../rules/chart-professional.md)及[生效批次范围](../rules/chart-professional-scope.json)：新增图须为有数据意义的曲线、柱状或其他专业统计/工程图表，不插示意图；有公式关联时，解释尽量自然沿用原公式关键符号，讲清系列、计算和变化，结合Word上下文。不要强行给无关图配公式，不删除源文原图。范围清单中的既有批次（含在做案件）和已做成果不因本条返修、重验或重启。

执行提速遵循[分阶段调度与简化验收协议](../rules/execution-efficiency.md)。建设/普通返修最多8案并行；等待录制/审查不占建设槽。新版repair_final只修图文/代码/UI/材料，父执行器按画面输入变化再进入录制队列，Word正文单独变化不重录。新批次默认使用2路可信录制并受内存准入约束，旧批次按manifest冻结的execution_profile执行；验收输出短证据ID，由父执行器核验审查前后文件一致后绑定哈希，保留原始答复与判断，不减少实际看图、读上下文和视频检查。对旧进程的切换要在安全检查点保存成果后完成。

- 源证据先行，独立陈列公式组、行内符号与图数分开登记。系统业务、后端和持久化优先，不能用图表大屏代替完整系统。
- 每案至少两张有意义的图，图数不绑定公式：一式可多图或无独立图，多式可共同支撑一图。必须执行[2026-09-24图表质量关卡](../rules/chart-quality.md)，禁止真值表换皮凑图；说明不限300–400字，要讲透计算、数值变化、原因及判断。每图PNG/CSV同一冻结计算快照；黑白专业图、图内无标题角注；图例在图内留白，与线/柱一一对应且无遮挡。禁止化工附图技能替换软通图。
- 最终图按文件哈希锁定；Word增补说明必须结合正文实施例合适位置的前后文重新组织，衔接自然、术语/对象/条件一致，不能把独立图表说明整段硬贴。说明无字数限制，新增标红，每图在正文对应说明中自然写入“请参考图N”等独立引用，不能只写图下图题。说明留在正文；仅新增图片和图题统一追加到全部原文之后，按图号排列、图题在对应图片下方。禁止图片夹入正文，也禁止把说明跟随图片搬到文末。保留原文/原公式/原图及其位置。最终 verify_docx 必须确认 all_requested_figures_at_document_end=true、all_requested_figures_referenced_in_body=true，最后修改后全页渲染，检查正文衔接、文末图片及下方图题。历史报告缺少该字段不冒充已核验位置与引用，也不自动重开旧批。
- 每案约10秒视频，只录合格的1–2个业务模块，预热/排演后录，不含难看的状态；独立验收者检查完整采样时间线和高分辨率关键帧。
- 网页和录制中的全部可见文字遵循 [新增文案规则](../rules/web-visible-copy.md)，不能出现模拟、虚拟、工程样本、模拟数据、工程示例等字样及英文替代；包括说明弹窗和后端返回到界面的字段。数据来源、演算性质和未验证范围集中留在工作区README.md，不改称实测；是否复制到成品遵循本批delivery_profile。Sol实际浏览器采集ui_text_audit及对应截图，脚本检查文字/覆盖/哈希，独立验收者对照截图和视频验收；不通过继续返修，受影响视频重录。
- 独立审核必须由真实CLI调用（普通gpt-6.1-sol/ultra，明确加急gpt-6-astra/low），不能建设者自评或写一句“切换独立验收者”。默认在Sol完成建设、自检及录制、脚本机械检查通过后，一次集中审核所有成果；可修复问题不通过就继续由GPT-6.1 Sol ultra处理，集中修好并自检后再交独立验收者，直到通过，不设固定两次上限。累计记录调用和CLI用量，恢复不重置。独立验收者只给简洁、有证据的修改清单，不建设、不写代码、不重读整批历史；复验聚焦修改及关联产物，无依据的风格偏好不阻断。缺材料执行[数据与材料自动补齐](../rules/material-sourcing.md)：先检索开源实现/公开数据，剩余输入用符合源定义的模拟数据和明确工程假设补齐并实际计算。用户已授权，不因缺实测、同批标定、历史、权重或设备回执暂停，不再请求调整验收范围。验收检查本地实现与可复现结果，未完成的现场接入/泛化验证写limitations；源文件不可读、核心定义无法解释或模型/额度/环境故障才报告具体阻塞。旧审核与新文件不匹配时失效。
- 新批次最终交付只含增补Word和模拟系统/视频，原件副本、图表资料、README、源码和过程证据保留在工作区。旧批次按冻结的full合同交付，不自动清理。历史交付文件夹名不属于web可见文案。资料真实性与限制集中写入README，不把演算数据冒充实测。

- `scripts/caseflow.ps1 control <批次ID> priority --value 10`：提高尚未开始阶段的排队优先级，可加`--case-id <ID>`只加急单案，不打断正在执行的付费调用。
- `scripts/caseflow.ps1 control <批次ID> resume-case --case-id <ID>`：外部故障已解除、用户已授权继续时，让当前新执行器重新调度该案；不会重复启动仍在跑或已交付的案。执行器已退出时用原run恢复。
- `scripts/caseflow.ps1 control <批次ID> drain`：让当前调用完成，在下一阶段边界保留状态后停下，不杀进程；后续`control <批次ID> continue`解除，再run恢复。仅用户明确要求暂停/维护切换时使用。

控制请求仅由显式命令产生，不定时扫描新材料、不后台唤醒。历史阶段耗时可用bundled Python执行`scripts/pipeline_metrics.py`汇总；并行阶段分钟数不能相加当作整批墙钟时间。新录制程序技术验证不等于案件视觉验收，也不承诺固定提速比例。
