# 按案件业务制作 Web

适用于本技能的系统建设及用户明确要求的界面调整。与 `system-data.md`、本案原技术材料一起使用。目标是不同业务有各自合理的工作界面，并且界面操作真实调用本案算法与持久化。

## 在现有建设计划中写清四项

直接从本案实施例、对象和用户任务确定：使用角色、最重要的日常任务、主工作区、两项关键交互。用一小段写入已有建设计划即可，不新建审批、设计问卷或额外模型阶段。已有明确材料就实施，不逐案要求用户确认风格。

主工作区先承载本案最有辨识度的对象；对象、信息组织和操作顺序决定布局。以下是可选择的方向，不是固定套版：

| 业务特征 | 主工作区方向 | 有意义的交互 |
| --- | --- | --- |
| 压力场、几何或图像检测 | 空间视图与局部检视台 | 选区、叠层、缺陷定位、局部复核 |
| 事件关联、故障调查 | 时间轴与事件关联视图 | 时间窗筛选、关联定位、处置前后对照 |
| 反应、训练或批次预测 | 批次工作台与参数结果对照 | 参数约束、版本比较、预测核准 |
| 农业、分区控制或流量调节 | 分区作业视图与控制曲线 | 分区选择、处方调整、反馈对照 |
| 排程、资源或能量调度 | 任务时段与资源占用视图 | 冲突定位、排程调整、执行进度 |
| 对象登记、审核或信息处理 | 工作队列与详情联动 | 条件组合、逐项处置、状态追踪 |

同批读取已有案件的简短设计画像，不重新打开全部成品。不同业务若仍是同一导航、同一指标卡排列、同一表格抽屉结构，先调整主工作区、信息层次或关键交互；仅换标题、颜色、图标不算差异。相同领域可以保留有用的操作习惯，不能为追求不同而破坏可用性。

配色用于区分对象、量或状态，字体、间距和密度服务于阅读。业务密集界面允许紧凑表格；空间或时间分析给主视图足够面积。装饰不占业务内容空间。通用表格、表单、认证和图表基础组件可以复用，页面结构与领域数据绑定按本案制作。

## 用户能理解的文案

页面、提示、错误、导出预览和初始化空状态使用业务语言。不出现“经计算生成数据”“生成数据”“演示数据”等制作过程说明；集中规则见 `ui-policy.json`。优先改为准确的对象、动作或状态，例如“批次记录”“预测结果”“待核对”。“生成报告”“计算结果”属于正常业务词，不一概禁用。不要替换成未经证实的“实测”“现场采集”“生产运行”等说法。

原材料、计算假设、数据性质和出处继续如实保存在内部证据中；修改界面文案不删除证据、不修改原 Word，也不改变算法含义。

## 建设时一次做对

沿已有浏览器自检核对主操作、详情/列表/统计同版本、错误反馈、空结果和导出。表单有明确标签，键盘焦点可见，提交期间有反馈；长表按业务分页或按需加载，图表选中对象与其他视图同步。截图用于判断布局与内容是否专业，不能用截图替代真实点击和业务断言。

异步结果在写入任何可见状态前核对请求发起时的对象ID、版本与当前请求序号；操作、计算、图表、提示和详情各自的回调都适用，不能只保护refresh。中途切换对象、改变筛选或关闭详情后，迟到结果不覆盖当前页面，也不重开抽屉；后台已完成的真实操作仍保留。建设内用一次延迟响应加切换/关闭动作验证本案实际消费路径，沿已有浏览器日志记录，不新增审核阶段。录制计划的搜索清空也实际执行一次，不能只检查非空输入。

在同一次high浏览器自检里，把这些实际页面状态的可见文字交给现有 `record.cjs` 导出的 `auditUiText` 检查，复用 `ui-policy.json`，问题在录制前修正；不另建文案检查模型，也不等整段视频录完才发现禁用文案。

一次查看主工作区和最关键详情，发现具体问题才定向修正。不要为每案强制生成视觉概念图、下载设计库、添加无业务用途的动画或启动独立设计审核会话。已有清晰界面无需为了新指南重新制作。
